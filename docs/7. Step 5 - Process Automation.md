# Step 5: Process Automation

In this final step, you will create a script that runs the complete model scoring and monitoring process. You will then configure a cron job that runs the script once every 10 minutes.

## Starter Files

For this step, you will work with:

- `fullprocess.py`, which will determine whether new data exists, check for model drift, and run retraining, deployment, diagnostics, and reporting when needed;
- the Python scripts completed in Steps 1–4;
- `config.json`;
- `ingestedfiles.txt` and `latestscore.txt` from the production deployment directory; and
- the deployed model in the directory specified by `prod_deployment_path`.

Run the project scripts from the repository root. Before completing this step, update config.json with paths relative to that root:

- `input_folder_path` points to `sourcedata`; and
- `output_model_path` points to `models` rather than `practicemodels`.

## Check for and Ingest New Data

The first part of `fullprocess.py` must determine whether any new data needs to be ingested.

1. Read `ingestedfiles.txt` from the deployment directory specified by `prod_deployment_path` in `config.json`.
2. Check the directory specified by `input_folder_path` and identify any files that are not listed in `ingestedfiles.txt`.
3. If new files exist, run the code in `ingestion.py` to ingest the available data.

Do not continue to the model-drift check when there is no new data. Without new data, there is no reason to train and evaluate a replacement model.

## Check for Model Drift

If new data was found and ingested:

1. Read the deployed model's score from `latestscore.txt` in the production deployment directory.
2. Use the deployed `trainedmodel.pkl` and the newly ingested data to make predictions.
3. Run `scoring.py` to obtain a score for the new data.
4. Compare the new score with the deployed model's score. If the new score is lower, model drift has occurred.

If the new F1 score is equal to or higher than the deployed baseline, skip retraining and redeployment. Keep the deployed model and its baseline score unchanged, and continue to diagnostics and reporting.

## Retrain and Redeploy

If new data exists and model drift has occurred:

1. Run `training.py` using the latest ingested data.
2. Use `scoring.py` to evaluate the newly trained model from `output_model_path` on `testdata.csv` in `test_data_path`. Save its F1 score as `latestscore.txt` in `output_model_path`.
3. Run `deployment.py` to copy the newly trained model, its newly calculated `latestscore.txt`, and the current `ingestedfiles.txt` to `prod_deployment_path`.

## Run Diagnostics and Reporting

After processing new data, run `apicalls.py` and `reporting.py` against the current deployed model, whether or not drift was detected. If drift occurred, first complete retraining, evaluation, and redeployment as described above. If no drift occurred, use the existing deployed model.

Use the configured test dataset for the confusion matrix and the API scoring request. Save the following second-run outputs even when no redeployment was needed:

- Save the new confusion matrix as `confusionmatrix2.png` for final submission.
- Save the new combined API output as `apireturns2.txt` for final submission.

Preserve the first-run files, `confusionmatrix.png` and `apireturns.txt`. When the deployed model and test data are unchanged, the second confusion matrix and model predictions or score may match the first run; this is expected. Timing and dependency-check results may vary. Do not force retraining or alter the baseline score just to produce different reports.

If there is no new data, stop before drift checking and report generation.

## Cron Job for the Full Pipeline

Your completed `fullprocess.py` automates the important model deployment, scoring, monitoring, and reporting steps. Configure the Workspace to run this script once every 10 minutes without manual intervention.

1. Start the cron service in the Workspace:

    ```bash
    service cron start
    ```

2. Open your crontab:

    ```bash
    crontab -e
    ```

3. Add a one-line cron job that runs fullprocess.py once every 10 minutes. Use the correct absolute path for your project and Python executable.

4. Save the file and exit the editor.

5. Verify the installed cron job:

    ```bash
    crontab -l
    ```

6. Save a copy of the one-line cron job as `cronjob.txt` for submission.

**Azure Pipelines is an optional extension**: Azure DevOps users may also experiment with a scheduled Azure Pipeline that runs `fullprocess.py`. This does not replace the required cron exercise or `cronjob.txt` submission. Hosted pipeline agents are temporary, while this project depends on model and monitoring files created by earlier runs. A pipeline-based implementation must restore and persist those files through an approved durable storage service. YAML schedules use UTC and are subject to scheduled-run limits; a 10-minute schedule produces 1,008 runs per week, slightly above Azure Pipelines' documented limit of approximately 1,000 scheduled runs per pipeline per week. Do not submit a private pipeline URL as project evidence. Include the same required scripts and generated outputs in your ZIP.
